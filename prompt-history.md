# Prompt History

Selected prompts from building this project with Claude Code, with what came of each.

Every prompt I typed was auto-captured to `prompt-log-raw.md` by a `UserPromptSubmit` hook, so this
is curated from a complete record rather than reconstructed from memory. What follows is the subset
that best shows the thinking — especially the places where I questioned or rejected what the AI
suggested.

---

## Planning

### Setting up the workflow before writing any code

> First, I wanna set up Claude code with whatever agents commands skills to manage this project and
> track the work and commit and push to github and all of that. when we plan the project, I wanna
> create a file for the whole plan. And then we can break it into manageable chunks for AI to work
> on. And we can keep track of it with a sub agent doing work. Something like that?

This came before any code existed. The result was `PLAN.md`, a ten-chunk breakdown, and a `/build`
command that runs the same loop every time: build one chunk, explain it, commit it, quiz me on it.

### Making sure I'd understand the code, not just possess it

> It's not about manually entering the code or writing the code myself. It's more about efficiently
> using AI to build this app that it requests I build. It's imperative that I know what the code
> means. Because I know that they're gonna interview me and what they're gonna ask me, I need to be
> able to answer. So, rather than having a sub agent just write all the code and me not understand
> what it means, maybe have a sub agent write all the code, and then create a report for what every
> bit of code did so that I can understand what it means. Like a builder teacher agent.

This produced the **builder / explainer split** that shaped the whole project. One agent writes a
chunk. A *separate* agent then reads the finished code with no knowledge of what the first intended
and explains what it actually does, in plain language, into `docs/code-notes.md`.

That separation turned out to matter more than I expected. Because the explainer only sees the code,
it kept surfacing things the builder hadn't mentioned — including a latent bug one chunk before it
would have bitten, and a divide-by-zero that was producing `Infinity cups flour`.

### Committing as I went

> Is the builder set up to commit the code as it goes? Rather than committing it all at the end?

Asked because the course requires a commit history that shows the project evolving. The answer was
to make the commit a non-optional step inside `/build` rather than something I'd have to remember.
The repo has a separate commit for every chunk.

## Pushing back

### Rejecting two formatting suggestions in a row

This is the exchange the whole project turned on. The problem: scaling ⅓ cup by 1.75× gives
`0.5833 cups`, which nobody can measure.

The AI's first suggestion was to snap to the nearest familiar fraction — `½ cup`. Its second, after
I questioned that, was to step down one unit — `9⅓ tbsp`. I didn't like either:

> the single thing i would push back on is i dont want 9 and 1/3 tbsp. i would prefer the largest
> amount of cups possible here, then using the other units to carry the rest. so 5 cups and 2tbsp
> possibly even 5 cups, 5tbsp, 1 tsp. type stuff. so i imagine math that will take whatever and
> reduce it to X leftover Y, do it again to find the nearest whole metric, then keep doing it so
> that whatever we do leave out at the end is the most negligible. nothing like .3tsp

What I was describing turned out to be the **change-making algorithm** — the same logic a cash
register uses to pick coins. Convert to the smallest unit, take as many of the largest as fit, carry
the remainder down.

It's not just nicer to read. It's *more accurate*:

| Approach | Result | Error |
|---|---|---|
| Snap to a fraction (AI's first suggestion) | `½ cup` | 8.3% off |
| Step down one unit (AI's second) | `9⅓ tbsp` | 0.4% off |
| **My ladder** | **`9 tbsp 1 tsp`** | **exact** |

⅓ cup is 16 tsp exactly, ×1.75 is 28 tsp, which is 9 tbsp and 1 tsp with nothing left over. That
exactness isn't luck — because each unit divides evenly into the next, the division never introduces
rounding error of its own.

The AI then pointed out a case I'd missed: my own example, `5 cups 5 tbsp 1 tsp`, is exactly
`5⅓ cups` — simpler to read and one measuring cup instead of three. So decomposing isn't *always*
better. The final rule is **fraction first, decompose only when the fraction would be meaningfully
wrong**, with the line at half a tablespoon.

This is chunk 5, and it's the part of the codebase I understand best, because it started as my idea
and I had to argue for it.

### Not accepting a claim I couldn't verify

The AI told me the recipe text was being generated by JavaScript rather than typed into the HTML. I
didn't buy it from looking at the page:

> that wasnt very obvious to me because the page currently just displays it as text and I guess you
> injected that text via JS? i mean we currently dont have input fields on the page, so it all just
> looks like static text... no way for me to differentiate it from imaginary user text being input
> and actual static html

I was right that the rendered page gives you nothing to go on — injected text and static text look
identical. The resolution was learning the actual tool: **View Source** shows the HTML file as it
arrived from disk (an empty `<div id="recipe">`), **Inspect** shows the live DOM after JavaScript ran
(the same div full of `<li>` elements). The difference between those two views *is* the proof.

That's now how I check whether JavaScript ran at all, and it's the honest answer to "how did you
verify it worked?" — better than "it looked right."

### Calling out that the visible app had fallen behind

Four chunks in, there was a lot of working logic and still nothing you could type into:

> so You build all the internal logic, but you have yet to add any of the HTML forms so that they're
> actually connected... Did you do the REGEX pattern? Did you do the REGEX pattern?

The answer was no — the parser was chunk 7 and we were on chunk 4. The dependency order was
defensible (the parser needs somewhere to put its output), but the effect was that the app looked
static for a long stretch. We swapped the build order to put the editor ahead of the ladder so there
was something real on screen sooner.

## Designing the parser

### Asking whether it was even possible

> do you think we could manage doing a text drop, where it somehow parses the lines for us and breaks
> it up into ingredient and amount? Im not sure how it would work, given potential formatting, etc.
> idk if there is some sort of Regex pattern or something that can catch it when recipes like this
> might not be standardized in anyway.

The AI's first answer had been that free-text parsing was fragile and structured fields were safer.
Pushing on it produced a better answer: recipe lines are far more regular than they look — nearly all
fit `[amount] [unit] [ingredient]` — and the parts that *don't* parse can be handled by design rather
than by cleverness.

That became the rule the whole feature rests on: **flag what you can't read, never drop it.** The
parser fills in what it understands, marks what it doesn't, and the user fixes it in place. Perfect
parsing is impossible and the course forbids AI features, so the design answer is to make
imperfection cheap rather than to chase accuracy that can't be reached.

### Specifying the edge cases myself

> can you write in some sort of rule that could possibly take lines with no number or fractions,
> leave them as is (salt and pepper to taste is relevant at any metric) and things like 2-3 cloves
> can just be scaled up with 4-6 cloves, though i understand its a bit harder to do that
> mathematically because 2-3 isnt a number you can standard math on. and then yes it sounds like we
> have some sort, other last function that what...will inevitably have to do some sort of rounding
> math? is that an if else statement that will look if its closer to X or Y?

Three things came out of this:

1. **Lines with no number pass through untouched.** "Salt and pepper to taste" is correct at any
   batch size.
2. **Ranges were easier than I thought.** I assumed `2-3` needed special maths. It doesn't — a range
   isn't a special kind of number, it's *two ordinary numbers with a dash between them*. Split,
   scale each half with the function that already exists, rejoin.
3. **My instinct about the rounding was right but the implementation was better.** I described a
   chain of if/else comparing against midpoints. The AI's version loops over a list of measurable
   fractions and picks whichever is *closest* — so the midpoints derive themselves. Nobody writes
   "if above 0.4166 use ½". Add `⅛` to the list later and every boundary rearranges itself
   correctly.

### Specifying the interface

> if there is anything we can do to make it a little more interesting or useful than broad input form
> for ingredients... maybe some sort of prompting to have users look over the added recipe or like
> the ability to make edits, obviously so like when you uploaded, it should present itself in the same
> way, as if you added it manually line by line and then those lines are editable before you choose
> how many people to scale it

This turned into the project's main architectural rule: **paste and manual entry converge on one
editor.** A pasted recipe and a typed one are indistinguishable by the time anything reaches the
scaling code.

That's what makes the parser safe to be wrong. Its mistakes are just wrong values in editable fields,
corrected exactly the way you'd fix your own typo.

## Catching problems

### Personal information heading for a public repo

Before the first push, a scan turned up my email address inside the raw prompt log:

> just redact the email and any PII in there i want the prompt log in the project

Redacting the file wasn't enough. My email was also embedded in the **metadata of every commit** —
git stamps the configured address into each one, and GitHub displays it publicly. Deleting a line
later wouldn't have helped either; it stays in the commit history.

Because nothing had been pushed yet, all four commits could be rewritten cleanly and the address
swapped for a GitHub `noreply` address. Verified afterwards by searching every object in the repo's
history, not by assuming.

### A bug found before it happened

The explainer flagged that `renderRecipe` only ever *added* elements to the page and never cleared it
first. Harmless at the time — the function ran once. But the next chunk redraws on every keystroke,
which would have stacked a second full copy of the recipe under the first on every keypress.

It was fixed in the chunk that made it reachable, before it ever appeared on screen.

### A bug found by actually running the code

The explainer suspected that clearing the "Makes N servings" box would divide by zero. Rather than
take that at face value, the real `script.js` was loaded into Node against a stub browser and run:

```
blank "Makes N servings"  →  multiplier: Infinity  →  displays "Infinity cups flour"
both boxes blank          →  multiplier: NaN       →  displays "NaN cups flour"
normal case (6 from 4)    →  multiplier: 1.5       →  displays "2¼ cups milk"  ✓
```

Confirmed, not guessed. The root cause was an asymmetry: the function reading an *ingredient's*
amount box already guarded against a blank value, but the function reading the *servings* box didn't
— the same guard applied in one place and not the other, purely by omission. Fixed in chunk 10.

## What I'd say about working this way

The single most useful decision was separating the agent that writes code from the agent that
explains it. An AI describing its own work tells you what it meant to do. A second one reading it
cold tells you what's actually there — including the parts that are fragile, hard-coded, or
debatable. Most of the real problems in this project surfaced that way.

The second most useful was refusing to accept output I couldn't verify. "It looks right on the page"
is not verification. View Source versus Inspect, and running the actual functions against actual
inputs, are.
